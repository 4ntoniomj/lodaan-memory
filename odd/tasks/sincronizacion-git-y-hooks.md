# lodan: git sync between machines and lifecycle hooks

Objective: sync the lodan memory between machines through an encrypted private git repository, and add the compaction and subagent-stop hooks that work without AI discipline.
Branch: `feat/sincronizacion-git` (from `feat/lodan-lotes-relaciones`, approved by the user in L2). Delivery: `single-pr`. Test runner: `go test ./...` (DB tests need `LODAN_PG_BIN_DIR=C:/Users/4ntoniomj/AppData/Local/lodan/runtime/pg/Library/bin`).

## Specs

The user's prompt is quoted verbatim in L1; the approved proposal is in L2. Quotes in «» are from L1.

### Sync

- **S1 — Global identity.** Every memory gets a stable global `sync_id` (UUID) that never changes and is unique across machines; existing records get one in the migration. Sessions keep their ULID `id`, topics are identified by `slug`, relations by (source `sync_id`, target `sync_id`, kind). Local numeric ids never travel in the files. «importar sea idempotente: importar dos veces no duplica, y los ids locales nunca viajan como referencia».
- **S2 — Migration 0003.** Adds what S1, S3 and S6 need without changing any existing data (titles, contents, statuses, relations, sessions and topics identical before and after). Tested on a temporary database; on the real one only after a full `pg_dump` in `AppData\Local\lodan\backups-manual`.
- **S3 — Export only what changed, exactly once.** Exporting writes one batch file with every memory, relation, session and deletion created or changed locally since the previous export, and nothing else. A second export with no local changes writes no file. Changes that arrived by import are not exported again.
- **S4 — File format and encryption.** Files live at `changes/<machine-id>/<UTC timestamp>-<n>.jsonl.age` inside the repository. Content: JSON Lines (one header line with format `lodan-sync/1`, the machine id and the creation time, then one line per change) encrypted with `filippo.io/age` to an X25519 recipient. «en GitHub solo debe verse contenido ilegible»: no title, content, topic or client name may appear in the file bytes. Embeddings, embedding model, `config.json`, `secret` and `lodan_settings` are never written. Each machine writes only to its own folder.
- **S5 — Import.** Importing applies every not-yet-imported file of the other machines' folders, oldest first, and remembers which files it applied (importing the same file again changes nothing). Imported memories arrive without embedding and the maintenance `FillPending` computes it. Topics are created by slug when missing. A file that cannot be decrypted with the local key is not applied and the error says `no se pudo descifrar <ruta>: la clave no coincide`; the other files are still applied.
- **S6 — Merge rules.** «sin perder ni duplicar nada».
  - (a) Unknown `sync_id` → the record is created with its status, topics, session and dates.
  - (b) Status only moves from active to superseded/invalidated: «un registro sustituido o invalidado en una máquina lo queda también en la otra». An import never reactivates a retired record.
  - (c) Same record edited on two machines without either having seen the other's edit → the version with the most recent `updated_at` wins (deterministic tie-break) and the other version is kept as a superseded copy related to the winner with `supersedes` («la otra versión queda como historial»). If one machine edited on top of the other's version, it simply replaces it and no copy is created.
  - (d) Two different active records with the same `key` → the most recent keeps the key, the other stays active without key, both are related as `contradicts` (confirmed), and the import result lists the pair so the user is asked which one is true. Both machines converge to the same state.
  - (e) Two different active records with identical content → they are treated as one record (the incoming `sync_id` becomes an alias of the local one); later changes or relations that reference either id apply to that record.
  - (f) A memory deleted physically on one machine is deleted on the other; a deletion wins over any edit of the same record, and a copy arriving later does not recreate it.
  - (g) Relations are joined by (source, target, kind); their state follows the most recent change. A relation whose records have not arrived yet is applied when they arrive.
  - (h) Sessions are joined by id; `ended_at` and `summary` keep the most recent non-empty value; session topics are joined.
- **S7 — CLI.** `lodan sync init --repo <url> [--key <file>]` clones (or creates) the working copy, creates the key file if it does not exist (never overwrites one) and stores the repository URL in `config.json`; it prints the key path and the warning `Guarda una copia de la clave fuera de este equipo: sin ella el contenido del repositorio no se puede recuperar.` `lodan sync push` exports, commits and pushes; `lodan sync pull` pulls and imports, and prints the contradictions to resolve. Both use the system `git` with the user's configuration; no credentials in code, config or lodan. Without `init`, push/pull fail with `la sincronización no está configurada: ejecuta lodan sync init --repo <url>`. Help text and README updated.
  - Interface (decided 2026-10-17): `config.json` fields `sync_repo` (git URL), `sync_machine` (machine id, default the host name normalised to `[a-z0-9-]`), `sync_key_file` (default `config.DefaultSyncKeyFile()` = `os.UserConfigDir()/lodan/sync.key`); working copy at `<DataDir>/sync-repo`. Package API `gitsync.Init(ctx, Config) (InitResult, error)`, `gitsync.Push(ctx, pool, Config) (ExportResult, error)`, `gitsync.Pull(ctx, pool, Config) (ImportResult, error)` with `Config{RepoURL, Dir, MachineID, KeyFile}`; the remote branch is `main`. `lodan sync pull` prints one line per contradiction: `contradicción en la clave <key>: #<kept> conserva la clave, #<other> no; dime cuál es el bueno`.
- **S8 — Periodic sync.** New `config.json` field `sync_interval_minutes` (default `0` = off, env `LODAN_SYNC_INTERVAL_MINUTES`). When > 0 and sync is configured, the service supervisor runs pull then push every interval; failures are logged and never stop the service.
- **S9 — Key handling.** The key file defaults to a path outside the lodan data directory (so backups never carry it) with owner-only permissions; it is never written to the repository or to lodan. README explains how to keep it and move it to another machine, and warns that losing it makes the repository unrecoverable.

### Hooks

- **S10 — `lodan hook compact --client <name>`.** Reads the event JSON from stdin.
  - When `hook_event_name` is `PostCompact` and `compact_summary` is non-empty: stores it as the summary of the most recently active open session of that client, without closing it; with no open session it creates an ended session with that summary. Prints nothing.
  - Any other event (including empty or invalid stdin): prints to stdout the recovery instructions («llamar a `recall` en lote con los temas en curso antes de seguir») followed by the summary of the last ended lodan session of that client, if any.
- **S11 — `lodan hook subagent-stop --client <name>`.** Reads the event JSON from stdin. Takes the subagent's final message from `last_assistant_message`; when it has no `## Key Learnings` block and `agent_transcript_path` is given, uses the `message` input of the last `SubagentHandback` tool call in that transcript. Extracts the last `## Key Learnings` block (numbered items, at most 5) and saves each item as a `note` in the topic of the project, derived from the event's `cwd` (the git repository root folder name, else the folder name). No block → saves nothing. Items that look like secrets (passwords, tokens, API keys, private keys, `AGE-SECRET-KEY-`) or Spanish DNI/NIE numbers are not saved. Prints nothing on stdout.
- **S12 — Hooks never block.** Both hook commands always exit with code 0, finish within their timeout and print nothing harmful when lodan's database is unavailable or the input is malformed (errors go to stderr).
- **S10-S12 interface (decided 2026-10-17).** Package `lodan/internal/hook`: `Compact(ctx, deps *Deps, client string, in io.Reader, out io.Writer) error`, `SubagentStop(ctx, deps *Deps, client string, in io.Reader) (saved int, err error)`, `ExtractKeyLearnings(msg string) []string`, `ProjectTopic(cwd string) string`, `Deps{Pool, Memory, Sessions}`; `deps == nil` means lodan's database is unavailable. Recovery text (constant `hook.RecoveryInstructions`): `lodan: el contexto se acaba de compactar. Antes de seguir, llama una vez a recall de lodan en lote (queries) con los temas en curso de esta conversación y continúa con lo que devuelva.` followed, when there is one, by the line `Última sesión de lodan (<client>, <AAAA-MM-DD>): <summary>`. Saved notes: content = the item text, title = the item up to 80 characters (cut at a word boundary, `…` when cut), kind `note`, topic = `ProjectTopic(cwd)`, session of the client. Items must have at least 20 characters and 4 words. CLI: `lodan hook compact|subagent-stop --client <name>` reads stdin from the package variable `stdin` (default `os.Stdin`), never starts PostgreSQL (connects only if it is already running) and always exits 0.
- **S13 — Install the hooks** in each client where the event exists, without removing existing hooks: Claude Code (`SessionStart` matcher `compact`, `PostCompact`, `SubagentStop` in `~/.claude/settings.json`), opencode (plugin using the compaction hook and the end of the `task` tool, verified against the installed version), Antigravity (`SessionStart` only, if its output reaches the model; nothing for compaction or subagents: «No lo simules»). `lodan install` registers them idempotently so a second machine gets them too.
